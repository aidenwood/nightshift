# Recipes

Four shapes of long-running work, and how each maps onto a run.

---

## 1. Render / GPU queue

The original case. Expensive items, high failure rate, a hard window.

```bash
cat shots.jsonl        # {"id":"s01","shot":"wide-dawn","seed":4411}
nightshift start renders \
  --until 8h \
  --goal "One usable take per shot at 704x1280" \
  --items shots.jsonl \
  --freeze scene.py,prompts/character.md
```

Loop:

```bash
while true; do
  OUT=$(nightshift next renders --json); CODE=$?
  STATE=$(echo "$OUT" | jq -r .state)
  [ "$STATE" = "done" ] && break
  [ "$STATE" = "stopped" ] && break

  if [ $CODE -eq 3 ]; then
    # Budget left, queue empty. Vary a parameter and keep going.
    ./more-seeds.sh | nightshift add renders --items -
    continue
  fi

  ID=$(echo "$OUT" | jq -r .item.id)
  if ./render.sh "$OUT"; then
    nightshift done renders "$ID" --note "out/$(ls -t out | head -1)"
  else
    nightshift fail renders "$ID" --reason "render exited $?" --requeue
  fi
done
nightshift report renders --out MORNING.md
```

**Why `--freeze scene.py`:** a scene module edited at 2am while shots 1–6 are
already rendered gives you a set that cannot be cut together. The run will tell
you instead of handing you the mixed set.

**Why `--note` is the output path:** a render almost never stores its own
inputs. The note is the only link from the file to the job that made it.

## 2. Content batch (blog posts, product copy, descriptions)

Many cheap items, one shared style definition that absolutely must not move.

```bash
nightshift start blog-night \
  --until 07:00 \
  --goal "One post per cluster: 900+ words, 3 internal links, house voice" \
  --items clusters.json \
  --freeze house-style.md,brand-voice.md
```

`clusters.json`:

```json
[
  { "id": "offline-maps", "task": "offline hiking maps", "angle": "what breaks without signal" },
  { "id": "grade-system", "task": "australian walk grading", "angle": "what grade 4 actually means" }
]
```

The frozen style guide is the whole reason this works as a batch rather than as
20 unrelated posts. If you spot a wording problem at post 11, **queue the
correction** — `nightshift add` a fix-up item, or note it for the next run.
Editing `house-style.md` live gives you 10 posts in one voice and 10 in another.

## 3. Migration / audit sweep across many repos

Low failure rate, high item count, and resumption matters because the sweep
takes longer than one sitting.

```bash
ls -d ~/code/*/ | nightshift start audit --until 6h --items - \
  --goal "Every repo: lockfile committed, CI green, no secrets in git history"
```

Each item is a directory path string. Because state is project-local by default
and this run spans many projects, pin it:

```bash
nightshift start audit --dir ~/.nightshift --until 6h --items -
```

Through-day rather than overnight: pair with a scheduler for the wake-ups and
let nightshift hold the state, so each wake-up *resumes* instead of restarting.

## 4. Loop-until-dry discovery (bugs, edge cases, opportunities)

The item count is unknown at the start — which is exactly the case where
"finished the queue" means least.

```bash
nightshift start bughunt --until 4h --goal "Find and confirm real bugs in src/"
nightshift add bughunt --items '["sweep: auth","sweep: payments","sweep: uploads"]'
```

When the sweeps finish, `next` returns `idle`. That is the signal to spawn the
*next* round from what the last one found — new areas suggested by the bugs
already confirmed — not to stop. Keep going until two consecutive rounds return
nothing new, then `stop --reason complete`.

This is the pattern `idle` was designed for: a simple "the queue is empty"
check would have called it done after round one.

## Things that bite

**Don't freeze a file that's generated by the build.** It will change on the
first build and contaminate the run for no reason. Freeze the *source*.

**Items are claimed in order, fresh first.** An item claimed but never completed
goes to the back, so a crash is retried but a forgotten `done` doesn't stall the
night. Three claims without completing and it's abandoned and reported.

**`--requeue` is usually right on `fail`.** A transient failure at 2am should be
retried at 3am. Leave it off only when the failure is definitional — the item
itself is wrong, and retrying it will fail identically.

**Put the evidence in `--note`.** "Done" is not a result. A path, a count, a
seed, a URL is.
